# Development workflow

The Rev A hardware choice is not reopened by this work. All firmware guards and hardware gates stay fail-closed. Python tests, native C++ helper tests, and SPICE runs are different kinds of evidence; none authorizes connecting a person.

## Setup

Work from the repository root. Python 3.11 is the minimum supported version; the normal development interpreter is 3.13. CI checks both. Install the pinned environment manager and synchronize the locked project, development tools, and optional serial dependency:

```bash
python -m pip install uv==0.12.18
uv sync --locked --all-extras
uv run --locked pre-commit install
uv run --locked python -m tools.check
```

No virtual-environment activation is required for `uv run`. Use the repository's `.venv` interpreter in your editor. Enable Ruff formatting/linting and Pyrefly diagnostics there; the command-line checks remain authoritative.

`uv sync` installs this repository as an editable Python package. Do not add `sys.path` workarounds or rely on pytest to make otherwise broken imports work. The tests include an import from outside the checkout.

## Routine commands

```bash
# Entire ordinary quality gate: formatting, lint, types, complexity,
# architecture, hardware contract, software tests, and branch coverage.
uv run --locked python -m tools.check

# Focused test-first development; run the relevant failing test first.
uv run --locked python -m pytest tests/test_analog.py -q

# Full discovery includes hardware/rev_a/test_baseline.py.
uv run --locked python -m pytest --collect-only -q

# Apply only the configured safe lint fixes, then format.
uv run --locked ruff check --fix .
uv run --locked ruff format .

# Hooks can be exercised before committing.
uv run --locked pre-commit run --all-files
```

The ordinary check selects tests not marked `native` or `integration`. The native command below runs those separately and actually executes ngspice and the longer localhost replay. A plain `pytest` run collects all tests; tests needing unavailable native tools may skip, so do not equate its exit status with native-tool verification.

## Required native integration

On Debian/Ubuntu:

```bash
sudo apt-get update
sudo apt-get install --no-install-recommends ngspice g++ nodejs
uv run --locked python -m tools.check --native
```

The native mode requires ngspice, Node, and g++ or clang++. Their absence is a failure, not a simulator pass. It verifies the existing educational circuit against the independent nodal solution, tests portable firmware helpers, and exercises synthetic transport over real localhost UDP. It does not compile an ESP32 target, introduce the next Rev A SPICE model, measure hardware, or establish body-interface safety.

Logs, JUnit results, coverage, and `CHECK_REPORT.json` are written under ignored `reports/check/`; use `--out PATH` for a separate evidence directory. CI uploads these as artifacts, including on failure. Routine quality checks must not overwrite the committed historical `results/`, `VALIDATION.json`, `requirements-tested.txt`, or `SHA256SUMS.txt`. The old `python run_lab.py verify` command remains an explicit historical-style report generator and is not the DX gate.

## Test-first changes

For a bug or new behavior, write a focused test, run it, and verify that it fails for the intended reason. Make the smallest implementation change to pass; then refactor with the tests green. Add characterization tests before rearranging existing numerical code. Keep formatting-only work separate from intentional behavior changes.

Test invalid inputs and failure paths as well as successful output: malformed configuration, nonfinite values, dimensions, missing executables, timeouts, nonzero exits, malformed simulator output, and stale files. Use explicit random seeds and justified absolute/relative tolerances. Prefer independently derived expected values, symmetry, scaling, and limiting cases to snapshots generated by the implementation under test. Hypothesis complements explicit protocol boundary cases; it does not replace them.

The initial branch-coverage floor is configured in `[tool.lab-check]`. It gates `covered_branches / num_branches`, not coverage.py's combined line/branch percentage. Preserve or increase the floor; do not lower it or omit executable code merely to pass. A longer-term 90% target for core logic is not a claim that this migration has achieved it. Coverage cannot establish hardware safety or prove that tests were written first.

## Typing and complexity

Ruff uses explicit rule families and safe fixes, with Python 3.11 syntax and 100-character lines. There is no blanket `ALL` rule selection. Pyrefly uses `preset = "strict"` plus explicit Any, Any-return, unknown-type, and implicit-reexport diagnostics. `tools.check` treats Pyrefly warnings as gate failures too. Source, tests, hardware validators, and tools are included.

Use concrete dataclasses, TypedDicts, and literal unions where they clarify contracts. Validate JSON/NPZ and other external data at the boundary. `NDArray` dtype annotations do not validate shape, units, or finiteness; keep the runtime checks and tests. Do not replace validation with a cast or spread `Any` through the model to satisfy the checker.

complexipy's hard ceiling is 15 per function, with a design target of 10. Snapshot and ignore bypasses are disabled. Refactor around meaningful responsibilities, not arbitrary fragments that merely reduce a metric. Do not add whole-directory typing/lint exemptions or silently relax the limits.

## Public APIs and import boundaries

The analog implementation lives under `lab/analog/`; consumers keep the public `from lab.analog import InputNetwork, transfer` import. The package facade re-exports the existing API while `_model`, `_solver`, `_spice`, and `_report` remain internal. `hardware.rev_a` is the public hardware-contract facade. `lab/__init__.py` remains small.

Across components, use public interfaces. Within a component, use direct implementation imports instead of importing back through its facade. Keep facades free of file reads, simulations, sockets, or other application work at import time.

`__all__` documents exports; it does not make Python imports private. `tach.toml` supplies static enforcement: declared dependencies, explicit interfaces, no circular dependencies, no unconfigured root consumers, and checked TYPE_CHECKING imports. Boundary tests exercise both accepted facade imports and rejected implementation-module/dependency bypasses. Facade exports and interface definitions are tested for agreement. Do not export a helper solely to let unrelated tests import it; justify any narrowly scoped internal-test access separately.

## Dependency updates

`pyproject.toml` and `uv.lock` are the dependency source of truth. Versions are pinned and the lock includes the resolved transitive dependencies. `requirements.txt` and `requirements-serial.txt` are compatibility exports; tests reject drift. `requirements-tested.txt` records the older validation environment and is not an install input for current development.

After an intentional dependency update, regenerate the exports using the same options exercised in `tests/test_dx_contracts.py`:

```bash
uv lock
uv export --locked --no-dev --no-emit-project --no-hashes --no-header --no-annotate > requirements.txt
uv export --locked --no-dev --no-emit-project --no-hashes --no-header --no-annotate --extra serial > requirements-serial.txt
uv sync --locked --all-extras
uv run --locked python -m tools.check --native
```

CI uses `--locked`; it must fail rather than silently resolving a different environment. Pin GitHub Actions to immutable commit SHAs and keep ordinary workflow permissions read-only. Do not use `pull_request_target` to execute proposed code with write privileges.

## Review and merge

The `Quality` workflow runs `Python 3.11 quality`, `Python 3.13 quality`, and `Native integration`. Those are the checks to require in the repository's merge rules. Creating a workflow does not itself enable required-status branch protection; that is a separate repository setting.

Keep the DX review separate from hardware PR #1 and from new simulation behavior. Review changes against the hardware-baseline branch until #1 is merged, then retarget the DX PR to `main`. Do not merge either PR or change the selected hardware/gates as part of tooling work.
